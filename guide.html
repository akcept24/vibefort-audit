Check your AI-built app yourself

This guide is for founders who built their app with Lovable, Cursor, v0 or Bolt and are not security specialists. It walks you through the twelve checks that matter most for apps like yours — the ones behind the findings that repeat from app to app. The full pass takes about 15 minutes. You need your app's address, access to your builder or Supabase dashboard, and a browser; a few checks use one copy-paste command, and each one says exactly where to run it.

Why these twelve: AI builders optimize for "the demo works", and permissive defaults are what make features pass on the first try — an allow-everything database policy makes the insert succeed, instant confirmation makes signup "work". The published research points the same way: 45% of AI-generated code samples introduced a security flaw (Veracode, 2025 GenAI Code Security Report); researchers found 2,000+ high-impact vulnerabilities across 5,600 live vibe-coded apps (Escape.tech research, 2025); and in one study, 10.3% of 1,645 Lovable apps had their database access wide open (Lovable apps study).

One thing first: the public anon key in a Supabase or Firebase app is not a secret, and its presence is not a problem. It is designed to ship to the browser. Everything below is about what that key — the one anyone can pull out of your page source — is able to do.

Honest framing: this is a self-check. It finds the common holes, the ones strangers actually walk through. It is not a guarantee that your app is secure — nothing is — and the last section says plainly what it cannot see.

01

Your database answers anonymous reads

What to check. Your data sits behind a REST API. Anyone can ask it for table rows using the anon key from your bundle, and if row-level security is off or a policy is permissive, they get the data: every row, not just theirs — user emails, orders, messages, whatever you stored, with no password to crack.

Where to look. Find your project URL and anon key in your page source or the browser's Network tab, then run this in a terminal:

curl "https://<project>.supabase.co/rest/v1/<table>?select=*" -H "apikey: <anon-key>" -H "Authorization: Bearer <anon-key>"

BAD LOOKS LIKE: rows coming back from any table that is not deliberately public.

Fix: turn on row-level security for every table, with policies that return only the caller's own rows.

02

Anonymous writes work too

What to check. The same API accepts inserts, updates and deletes, and write policies are usually looser than read policies. A table can be read-closed and write-open, which is how apps collect spam signups, poisoned leads and edited prices. Reads leak what you have; writes let strangers change it.

Where to look. On a staging copy if you have one: POST one clearly marked test row with the anon key, then try to update and delete it — and delete it afterwards either way.

BAD LOOKS LIKE: a 201 ("created") answer, or your update or delete going through. That means anyone can write to that table.

Fix: write policies that require a signed-in user who owns the row — no anonymous writes.

03

Your database functions are callable by strangers

What to check. Postgres functions exposed at /rest/v1/rpc/ often run as SECURITY DEFINER: they execute with the owner's privileges and bypass row-level security by design. Supabase grants EXECUTE on new functions to anonymous and signed-in users automatically. If a function moves money, grants a plan or reads across users, the function endpoint is the gate now, and it stands open.

Where to look. Search your app bundle for /rpc/ to list the functions, then call one with the anon key and harmless parameters.

BAD LOOKS LIKE: a function that changes state or crosses user boundaries answers an anonymous caller.

Fix: revoke EXECUTE from the anonymous role and grant it deliberately, function by function.

04

A real secret shipped in your JavaScript

What to check. Supabase hands you two keys: the anon key, public and fine, and the service_role key, which bypasses all row-level security — it is the master key, and it looks almost identical to the anon key. Builders paste the wrong one into frontend variables more often than anyone admits, and live Stripe and AI provider keys travel the same route.

Where to look. Download your production JS bundle and search for eyJ (the start of every token). Decode a candidate locally — the payload is plain base64 — and never paste a live key into a decoder website. Also search the bundle for sk_live.

BAD LOOKS LIKE: a token whose role claim says service_role, or a live secret key, sitting in client code.

Fix: rotate the exposed key first, then move it server-side; client code ships only keys that are public by design.

05

A view quietly bypasses your row-level security

What to check. You locked the tables down, then built a reporting or dashboard view in the SQL editor. Unless the view is created with security_invoker = true, it runs with its owner's privileges, usually the database owner, and serves the underlying rows to anyone allowed to read the view. An attacker does not need your tables. The view is enough.

Where to look. Query each view through the REST API with the anon key, exactly as in check 01, and compare the answer with what the base table returns.

BAD LOOKS LIKE: the view returns more than the caller would get from the table itself.

Fix: recreate the view with security_invoker = true, so the caller's own policies apply.

06

A column you revoked is still readable

What to check. Column-level permissions feel precise: revoke email or internal_notes from the anonymous role and move on. But a table-level SELECT grant overrides column revocations. The dashboard shows the column as restricted while the API still serves it.

Where to look. Pick your most sensitive column and ask for only that column, anonymously:

curl "https://<project>.supabase.co/rest/v1/users?select=internal_notes" -H "apikey: <anon-key>" -H "Authorization: Bearer <anon-key>"

BAD LOOKS LIKE: the values come back.

Fix: revoke the broad table-level grant, then grant back only the columns that are actually public.

07

Realtime subscriptions stream other people's rows

What to check. Supabase Realtime can broadcast row changes to subscribed clients. If a sensitive table has realtime enabled without policies governing who receives what, any signed-in user — sometimes any visitor — can subscribe and watch other users' data change as it happens.

Where to look. Create two accounts, A and B. As B, subscribe to changes on a table that holds A's private records (the Supabase client in the dev-tools console can do this), then change a record as A.

BAD LOOKS LIKE: A's changes arrive in B's console.

Fix: keep realtime off sensitive tables, or scope it so subscribers receive only their own rows.

08

Phone signup confirms itself

What to check. One unauthenticated request shows your auth configuration. If phone_autoconfirm is on and no SMS provider is actually configured, anyone can register any phone number, including one they do not own, and be instantly "confirmed". Every control that trusts a confirmed phone number — account recovery, payouts, identity checks — is built on that sand.

Where to look. Run this in a terminal and read the JSON:

curl "https://<project>.supabase.co/auth/v1/settings" -H "apikey: <anon-key>"

BAD LOOKS LIKE: phone_autoconfirm is on and no SMS provider is set.

Fix: require a real code from a configured SMS provider — or turn phone signup off entirely if you do not use it.

09

Your file storage is a public bucket

What to check. Uploads land in object storage: avatars, documents, ID scans, invoices. Public buckets and anonymous listing turn "users upload a file" into "anyone enumerates and downloads every file", and predictable file paths make the enumeration fast.

Where to look. With the anon key, list your buckets (GET /storage/v1/bucket), then list the objects inside one, then open one object URL in a private browser window.

BAD LOOKS LIKE: anonymous listing works, or a private file opens in the private window without signing in.

Fix: make the buckets private and serve private files only through signed, expiring URLs.

10

An AI endpoint answers without a login

What to check. Edge functions and API routes that call a paid model are the open relay of this era. The endpoint names sit in your client bundle, and if the function never verifies the caller's token, anyone on the internet can run up your AI bill: no account, no payment, your key.

Where to look. Find the function URLs in your bundle and call one with no Authorization header and a minimal valid payload.

BAD LOOKS LIKE: the endpoint does the work (a 200 answer) instead of refusing you.

Fix: verify the caller's token in the function — 401 for unauthenticated calls — and cap what one user can spend, server-side.

11

Wildcard CORS on your API and auth routes

What to check. Access-Control-Allow-Origin: * means any website can call your API from a visitor's browser. On a purely public, credential-free endpoint that can be acceptable. On auth and account endpoints it deserves a deliberate decision, not a default left over from making an error message stop.

Where to look. Run this in a terminal and read the access-control headers in the reply:

curl -s -I -H "Origin: https://evil.example" https://your-app.com/api/auth

BAD LOOKS LIKE: the reply allows * — or the foreign origin — on anything that touches accounts, sessions or payments.

Fix: replace the wildcard with an explicit allowlist of your own origins on API and auth paths.

12

No Content-Security-Policy, or one switched off politely

What to check. A CSP is the browser instruction that limits where scripts may load from. It is the main brake on cross-site scripting turning into data theft. Apps ship with no CSP at all, or with one weakened by 'unsafe-inline' for scripts, which lets injected inline scripts run: the header stays, most of the protection goes. Missing clickjacking protection usually travels with it.

Where to look. Run this in a terminal and look for the content-security-policy and frame headers:

curl -s -I https://your-app.com

BAD LOOKS LIKE: no CSP at all, a script-src containing 'unsafe-inline' or 'unsafe-eval', or framing left open to any site.

Fix: ship a CSP whose script-src has no 'unsafe-inline' or 'unsafe-eval' (use nonces or hashes), and restrict framing to your own origin or deny it.

The 15-minute summary

Tape this to the wall. Before you promote a build, confirm:

  • Anonymous reads of every non-public table refused
  • Anonymous insert/update/delete refused (tested on staging)
  • RPC functions not executable by anonymous users unless intended
  • No service_role key or live secret anywhere in the client bundle (check the token's role claim)
  • Views return no more than the underlying tables would
  • Sensitive columns refused at column level, not just hidden in the UI
  • Realtime channels deliver nothing about other users' rows
  • /auth/v1/settings: no self-confirming phone signup without a real SMS provider
  • Storage buckets private; no anonymous listing; signed URLs for private files
  • Edge functions and AI endpoints return 401 without a user token
  • CORS on API/auth paths is an allowlist, not *
  • CSP present without 'unsafe-inline' scripts; framing restricted

What this guide cannot see

These checks look at your app from the outside, as an anonymous visitor. Anything that exists only behind a login — the logic inside your account pages, what one signed-in user can do to another's data beyond the channels above — sits outside them. And a clean pass is a snapshot, not a promise: it means these twelve checks found nothing on the day you ran them. Apps change with every deploy; re-run the list when yours does.
