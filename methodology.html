How a ShipAudit scan works

We audit your live app from the outside, the way an attacker sees it. No source code, no repository, no dashboard, no credentials. You give us a URL and confirm the app is yours to test. This page describes what actually runs, what it cannot see, and what we refuse to do.

The method

01

Map the surface

We fetch your homepage and the scripts it loads, and we note the backend addresses your own code ships to every visitor's browser.

02

Probe the failure classes

We run the checks listed below against the live surface. Everything this step produces is a candidate, not a conclusion. Scanners over-report; we design for that.

03

Verify independently

On every paid audit, a second pass re-runs each candidate from scratch, in a clean context with no shared state. A finding reaches your report only if the cold pass reproduces it. If your site stops answering mid-check, the finding is marked unproven, never quietly confirmed or cleared. Error is not evidence.

04

Report

Each finding arrives with a severity, the business impact, the evidence, and a fix you can hand to your builder. Evidence is redacted: secret values and personal data are never copied into a report.

The free scan runs steps 01–02 and labels its output as raw surface evidence. The verification in step 03 runs on paid audits.

What we check

Exposed data APIs

If your app ships a Supabase or Firebase backend, we take the public anon key from your own page code and ask the database what it shows a stranger. The free scan counts the rows in the tables that answer; it never fetches the rows themselves. A Firebase database gets the same treatment: top-level keys only, never values.

Leaked keys in shipped code

We read the JavaScript your site sends to every visitor and inspect the keys inside it: tokens are decoded to read the role they carry, and other key shapes are matched by pattern. A public anon key is normal; it is designed to ship. A service_role key is not: it bypasses all row-level security. A live payment or cloud key sitting in a bundle is a different emergency: anyone who copies it can use that account. We report the pattern and where it sits. The value is never copied.

Input handling

Pages and forms that take input get two gentle probes: a quote that makes a broken database query show its error, and a marker string that should never come back to the page unescaped.

Known framework issues

If your app runs on Next.js, we test whether a published middleware bypass (CVE-2025-29927) opens a page that should sit behind a login.

Exposed files

We ask for the files apps leave behind by accident: .env, git metadata, JavaScript source maps, and the sensitive paths a robots.txt sometimes lists out loud. If a path answers with your app's generic fallback page, we report it as a fallback page, not as an exposure.

Headers, transport, cookies

TLS version and certificate expiry, the redirect from plain HTTP, the security header set (Content-Security-Policy, HSTS, clickjacking and MIME protections), cookie flags, and CORS on your homepage, API and auth paths, including whether any website can call them from a visitor's browser.

Email records

SPF and DMARC on your domain: the records that decide whether a stranger can send mail that looks like it came from you.

The Deep Scan widens the same checks. The free scan samples the first tables and scripts it finds; the Deep Scan probes every public table in the schema and scans every script the page loads.

What we never do

  • No writes. Every probe is read-only. We never insert, update or delete anything in your database, and we never push real data through your forms.
  • No credentials. The scan never logs in. It uses only the public key your own page already ships to visitors.
  • No load testing. Requests are throttled by design. The closest thing to a stress test is three gentle loads of your login page to see whether a rate limit pushes back.
  • No testing without authorization. The scan form and the audit brief both require you to confirm you own the application or have written permission to test it.

The limits

Public surface only. These checks see what an anonymous visitor can reach. Anything that exists only behind a login sits outside them.

A clean result is not a guarantee. It means the checks above found nothing on the day they ran. No honest audit can promise an app is safe.

Blocked checks are reported, not guessed. If your site rate-limits or blocks the scan, part of the coverage can fail. The report lists what was not covered instead of filling the gap.
