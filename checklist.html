12 holes in vibe-coded apps

If you built your app with Lovable, v0, Cursor or Bolt, the code that shipped was optimized for one thing: that the demo works. Nobody in that loop gets rewarded for the opposite property: that things which should not work don't. So AI-built apps fail in the same places. The generators reach for permissive defaults because permissive passes on the first try: an allow-everything database policy makes the insert succeed, instant confirmation makes signup "work", a wildcard header makes the API error go away.

Below are the twelve checks behind the findings that repeat. You can run most of them yourself with curl and your browser's dev tools. Each takes two to five minutes.

One thing first: the public anon key in a Supabase or Firebase app is not a secret, and its presence is not a finding. It is designed to ship to the browser. Everything below is about what that key, the one anyone can pull out of your page source, is able to do.

01

Your database answers anonymous readsIN THE FREE SCAN

Your data sits behind a REST API. Anyone can ask it for table rows using the anon key from your bundle, and if row-level security is off or a policy is permissive, they get the data: every row, not just theirs. User emails, orders, messages, whatever you stored, with no password to crack, because the key sits on your homepage.

CHECK IT: curl "https://<project>.supabase.co/rest/v1/<table>?select=*" -H "apikey: <anon-key>" -H "Authorization: Bearer <anon-key>" — good is an empty list or 401/403 on every table that is not deliberately public. (Our free scan runs this as a row count; it never fetches the rows.)

02

Anonymous writes work too

The same API accepts inserts, updates and deletes, and write policies are usually looser than read policies. A table can be read-closed and write-open, which is how apps collect spam signups, poisoned leads and edited prices. Reads leak what you have; writes let strangers change it.

CHECK IT: on a staging copy, POST one clearly marked test row with the anon key, then try to update and delete it; delete it afterwards either way. Good is every write refused: 401/403 or an RLS error. A 201 means anyone can write to that table.

03

Your database functions are callable by strangers

Postgres functions exposed at /rest/v1/rpc/ often run as SECURITY DEFINER: they execute with the owner's privileges and bypass row-level security by design. Supabase grants EXECUTE on new functions to anonymous and signed-in users automatically. If a function moves money, grants a plan or reads across users, the function endpoint is the gate now, and it stands open.

CHECK IT: search your bundle for /rpc/, then call one function with the anon key and harmless parameters. Good is permission denied for anonymous callers on anything that changes state or crosses user boundaries.

04

A real secret shipped in your JavaScriptIN THE FREE SCAN

Supabase hands you two keys: the anon key, public and fine, and the service_role key, which bypasses all row-level security. It is the master key, and it looks almost identical to the anon key; both are JWTs. Builders paste the wrong one into frontend variables more often than anyone admits, and live Stripe and AI provider keys travel the same route.

CHECK IT: download your production bundle, search for eyJ, and decode a candidate locally; the payload is plain base64, and you should never paste a live key into a decoder website. Read the role claim. anon is fine. service_role in client code is an emergency: rotate the key first, then fix the code.

05

A view quietly bypasses your row-level security

You locked the tables down, then built a reporting or dashboard view in the SQL editor. Unless the view is created with security_invoker = true, it runs with its owner's privileges, usually the database owner, and serves the underlying rows to anyone allowed to read the view. An attacker does not need your tables. The view is enough.

CHECK IT: query each view through the REST API with the anon key, exactly as in check 01, and compare the answer with what the base table returns. Good is the view returning exactly what the caller would get from the table itself, no more.

06

A column you revoked is still readable

Column-level permissions feel precise: revoke email or internal_notes from the anonymous role and move on. But a table-level SELECT grant overrides column revocations. The dashboard shows the column as restricted while the API still serves it.

CHECK IT: curl "https://<project>.supabase.co/rest/v1/users?select=internal_notes" with the anon key. Good is an error or an empty result. If the values come back, fix it at the table level: revoke the broad grant, then grant back only the columns that are actually public.

07

Realtime subscriptions stream other people's rows

Supabase Realtime can broadcast row changes to subscribed clients. If a sensitive table has realtime enabled without policies governing who receives what, any signed-in user, sometimes any visitor, can subscribe and watch other users' data change as it happens.

CHECK IT: create two accounts, A and B. As B, subscribe to changes on a table that holds A's private records (the Supabase client in the dev-tools console can do this), then change a record as A. Good is B receiving nothing about A's rows.

08

Phone signup confirms itself

One unauthenticated request shows your auth configuration: GET /auth/v1/settings. If phone_autoconfirm is on and no SMS provider is actually configured, anyone can register any phone number, including one they do not own, and be instantly "confirmed". Every control that trusts a confirmed phone number, account recovery, payouts, identity checks, is built on that sand.

CHECK IT: curl "https://<project>.supabase.co/auth/v1/settings" -H "apikey: <anon-key>" and read the JSON. Good is confirmation that actually requires a code from a configured provider, or phone signup off entirely if you do not use it.

09

Your file storage is a public bucket

Uploads land in object storage: avatars, documents, ID scans, invoices. Public buckets and anonymous listing turn "users upload a file" into "anyone enumerates and downloads every file", and predictable file paths make the enumeration fast.

CHECK IT: with the anon key, list your buckets (GET /storage/v1/bucket), list the objects inside one, then open one object URL in a private browser window. Good is private buckets refusing anonymous listing, and private files opening only through signed, expiring URLs.

10

An AI endpoint answers without a login

Edge functions and API routes that call a paid model are the open relay of this era. The endpoint names sit in your client bundle, and if the function never verifies the caller's token, anyone on the internet can run up your AI bill: no account, no payment, your key.

CHECK IT: find the function URLs in your bundle and call one with no Authorization header and a minimal valid payload. Good is a 401 for unauthenticated calls, token verification on in the function, and a server-side cap on what one user can spend.

11

Wildcard CORS on your API and auth routesIN THE FREE SCAN

Access-Control-Allow-Origin: * means any website can call your API from a visitor's browser. On a purely public, credential-free endpoint that can be acceptable. On auth and account endpoints it deserves a deliberate decision, not a default left over from making an error message stop.

CHECK IT: curl -s -I -H "Origin: https://evil.example" https://your-app.com/api/auth and read the access-control headers in the reply. Good is an explicit allowlist of your own origins on anything that touches accounts, sessions or payments.

12

No Content-Security-Policy, or one switched off politelyIN THE FREE SCAN

A CSP is the browser instruction that limits where scripts may load from. It is the main brake on cross-site scripting turning into data theft. Apps ship with no CSP at all, or with one weakened by 'unsafe-inline' for scripts, which lets injected inline scripts run: the header stays, most of the protection goes. Missing clickjacking protection usually travels with it.

CHECK IT: curl -s -I https://your-app.com and look for content-security-policy and x-frame-options. Good is a CSP whose script-src has no 'unsafe-inline' or 'unsafe-eval', and framing restricted to your own origin or denied.
